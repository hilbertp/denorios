# The safety-net suite passes in a fresh copy of the code

## Summary

The `slice-372-ac-2` survival guard asserted that four gitignored runtime files exist
and are writable under `REPO_ROOT`. In a fresh copy of the code they do not exist, and
in a full run they exist only because five other test files require
`bridge/orchestrator.js`, whose module load seeds them into whatever tree runs the
suite. So the guard was deterministically red when run alone in a fresh worktree and a
race in a full run — slice 383's mandated run lost that race.

It now builds its own git repository, commits the four files and runs `git rm --cached`
on them there, which is the only place the claim it makes (an index-only removal spares
the disk) can actually be observed. One strict `assert.deepEqual` over a new pure
helper replaces the `existsSync` / `doesNotThrow` pair.

Proved where it matters: in a fresh detached worktree of this branch, with all four
runtime files absent from disk, the file is **13 tests / 13 pass / 0 fail**. The same
fresh worktree with the pre-fix file checked out is **11 tests / 10 pass / 1 fail** —
the one failure being this guard.

## What changed

- `regression/helpers/runtime-files-survive.js` (added) — `missingOrUnwritable(root, rels)`,
  a pure function returning the rels that are absent or fail `R_OK | W_OK` under `root`.
  One `accessSync` answers both questions (ENOENT for absent, EACCES for unwritable).
  It creates nothing and seeds nothing, so a caller can point it at a fixture it owns.
- `regression/dispatch-execution/j-untracked-runtime-state.test.js` (modified) —
  - new fixture builder `makeUntrackedRuntimeRepo(label)`, built the way
    `makeLandingRepo` is built in `j-runtime-state-survives-landing.test.js:98-125`:
    `git init -b dev`, commit the four runtime files, `git rm --cached` them, ignore
    them, commit. Plus the two small locals it needs (`gitIn`, `write`) and the
    `SURVIVING_PATHS` / `LIVE_STATE` constants.
  - the guard rewritten against that fixture with one strict assertion.
  - two new tests (below).
  - header comment records why the check moved off `REPO_ROOT`.
- `regression/COVERAGE.lock` (regenerated by `node scripts/build-coverage-map.js`) —
  registers `slice-391-ac-1` and `slice-391-ac-2` against the test file with their
  `@ac-hash` values; 620 → 624 guards.
- `regression/AC-MANIFEST.lock` (regenerated by `node scripts/build-ac-manifest.js` in
  the second commit, which is where the `AC:` trailers are readable from HEAD). It adds
  `slice-391-ac-1` and `slice-391-ac-2` — as `legacy-backfill`, the same way 388's and
  389's tags stand in the committed lock, because the deriver's text step reads only
  *tracked* `bridge/queue` briefs and brief 391 is gitignored.

No product code changed: the fix *is* the test.

## Tests moved or weakened

One test changed, in place, keeping its tag and its `@ac-hash` line:

- `regression/dispatch-execution/j-untracked-runtime-state.test.js` —
  `slice-372-ac-2 untracking did not delete the files from disk` now reads
  `… from disk (slice-391-ac-1)` and asserts against a git repository it builds
  itself instead of against `REPO_ROOT`. Its `assert.ok(fs.existsSync(...))` and
  `assert.doesNotThrow(() => fs.accessSync(..., R_OK | W_OK))` are replaced by the one
  strict `assert.deepEqual(missingOrUnwritable(tmp, SURVIVING_PATHS), [], …)`, which
  checks presence *and* readability *and* writability for all four paths. Why: the old
  form asserted a fact about the tree running the suite, which no test in that file put
  there — a fresh copy has none of those files and the check could only ever pass by
  accident of load order.

**Trap 1, classification.** Checked against the gate's own engine, not by eye:
`node -e "classifyFileDiff(<git diff of the test file>)"` over `lib/assert-direction.js`
returns `{"slice-372-ac-2":"reworded","slice-391-ac-1":"tightened","slice-391-ac-2":"tightened"}`.
So the change reads as **reworded**, not loosened, and no `Test-Loosen-OK` trailer is
needed. (Getting there needed the assertion's message kept on the same source line as
the `deepEqual`: the engine's literal rule reads a removed literal with no added one as
loosened, and it scans line by line.) No other test was moved, renamed, skipped or
removed; the other `slice-372-ac-2` tests in the file are untouched.
